# Golden tests against real Docling

Four files, one purpose: hold our `DoclingDocument` output to what Docling itself
produces and accepts. Nothing here is hand-written — every file is either
generated by docling-core or by a real Docling conversion of a corpus document.
There is a reference for **every one of the 37 corpus documents**, and for the five
fixtures beside the corpus (`inventory.xlsx`, `q3_review.pptx`, `invoice_scan.png`,
`merged_table.rtf`, `nested_table.docx`) — **42 in all**.

| File | What it is |
|---|---|
| `DoclingDocument.json` | The JSON Schema `docling-core` generates from its own model. The committed copy is the contract our output is checked against. |
| `validate_with_docling.py` | Loads our documents with **docling-core itself**: pydantic validation (unknown fields, enum spellings, required fields) and `validate_tree` (children and parents agreeing). |
| `docling/<stem>.json` | Real Docling conversions of corpus documents, via `document.export_to_dict()` — the same bytes Docling writes to a `.json` file. |
| `regenerate.py` | Regenerates the conversions above. |

Provenance of the two generated kinds of file, which is worth being able to re-check:

```bash
# The schema: byte-for-byte what docling-core produces for its own model
# (verified against the committed copy — `diff` reports no difference).
DOCLING_PY=~/.venvs/pdfextractor-docling/bin/python
$DOCLING_PY -c 'import json,sys;from docling_core.types.doc import DoclingDocument;\
  json.dump(DoclingDocument.model_json_schema(), sys.stdout, indent=2)' \
  > test-data/golden/DoclingDocument.json

# What was installed when the committed copies were made.
$DOCLING_PY -c 'from importlib.metadata import version;print(version("docling-core"), version("docling"))'
# 2.101.1 2.138.0
```

The schema's `version` default (`1.10.0`) is what the exporter writes, and a test asserts
the two are equal — so bumping docling-core makes that test fail instead of letting the
two drift.

The Rust suite is `crates/cli/tests/docling_golden_test.rs`. It runs in two layers:

* **Without any Python**, from the committed schema: every document the CLI
  writes for the whole corpus must be a legal `DoclingDocument` — required
  fields, no field an item class does not allow, legal enums, references that
  resolve, and a hierarchy whose children agree with their parents' `$ref`.
  This is what found bugs 44 and 45.
* **With `DOCLING_PY`**, from the real library, which is the authority on the
  format and not a reimplementation of it.

```bash
# the schema layer, always; the library layer when a Python with docling-core is pointed at
DOCLING_PY=~/.venvs/pdfextractor-docling/bin/python \
  cargo test -p pdfextractor-cli --test docling_golden_test
```

The same folder is what the **desktop window's Compare mode** reads: point it at
`test-data/golden/docling/` and every document it converts is drawn beside the
reference for it, block by block. That mode uses the same definitions as this suite
where they overlap — the character-agreement figure under each panel is the one
printed here, equations excluded for the same reason — but it *shows* the rows this
suite judges, so it is for looking rather than for passing or failing. It also uses
more of the reference than this suite does: where both sides published a box for a
block (the PDF references here; the DOCX ones carry no geometry at all), two rows that
stand alone in the same place on the same page are joined into one, which is how a
drawing the two readings ordered differently is shown as one row instead of once a
side. The box takes part in the matching itself, too: where the words cannot say which
of two pairs is meant — a drawing a document lists twice, in one order on each side —
it is the place that decides, and a pair the two readings put in different places is a
**differs** row that says where each of them put it. It also reads this suite's segmentation the other way round: a reference item
whose characters run from one of our word boundaries to another lies *inside* one of
our blocks, and the panel says so (**contained**) — the same words, cut into items by
the other reading — instead of calling it text we are missing. Where the other reading
put an item it would have to hold between two that are ours, so no run reaches them, the
item is folded onto the row of the block whose words hold it, which says how many items
it took and keeps whatever that row already disagreed about. An item the reference wrote
with no letters in it at all — the dotted leader or the rule of a form's line — is taken
the same way, where a block of ours that *already holds words* of the reference there
holds it too: it stands among the fragments of that line and is part of it. The row names
such items apart from the ones taken by their words, and shows the reference's items in
the order the reference wrote them. A letterless item standing alone in one of our blocks
is the reference's own reading of that area rather than a piece of ours, and is left to
the joining by position, which pairs it and says on the row that the boxes are what paired
it. One that nothing of ours holds and that nothing of ours lies along — a line our reading
produced no block for at all — is **placed**: a row of its own that says what Docling wrote
and where it lies, counted apart from the rows only the reference has, so a form's remaining
leaders are answered rather than listed as text we are missing, and **drawn** — the box
outlined on an outline of the page it was found on, beside the row, so which line of the
form a leader belongs to is visible rather than read off coordinates (a page whose size the
reference never states is named without a picture).
`cargo test -p pdfextractor-ui --test compare_test` runs it over a few corpus
documents, and
`cargo run -p pdfextractor-ui -- --selftest ../real/math-nary.docx --selftest-ref docling`
does the same through the window — and writes what it converts into a temporary
directory of its own rather than beside this folder's documents, so a smoke test over
the corpus leaves both `real/` and the references exactly as it found them. `cargo test -p pdfextractor-ui --test corpus_report_test --
--nocapture` runs it over the whole corpus at once and prints the document-by-document
verdict mix, worst first — the report in `progress.md`; the notes below explain the
agreement figures it quotes for the four `.doc` references and for `README.md`.

The report is also a **ratchet**, not just a view. The numbers a run measured are kept in
the repository beside these references (`compare-baseline.json`: one entry per document,
with its rows, its verdicts, its placed rows and items, its joined rows and its character
agreement — and a `measured` block naming the OCR mode those numbers were measured with,
so a later run can tell whether its own settings match), and the test fails if any document's panel now says more `differs`, more rows
only ours, more rows only the reference, or holds fewer of the reference's characters than
that file remembers — naming the document and the count, so a change that fixes one
document and quietly breaks another cannot pass. The columns it does not ratchet (`same`,
`contained`, `notation`, `joined`) may move either way, because a row that changes *how*
the two readings agree is not a worsening — and a `differs` row cannot leave its column
without landing in one of the one-sided ones, which are ratcheted.

The **placed rows** are ratcheted too, as a *rate* rather than a count: a form's
letterless items are placed one row per line of the form and drawn one picture per page,
and what the baseline records is how many items those rows stand for. More rows for the
same items — `irs_f1040`'s 327 items coming back as 327 rows instead of 25, which no other
count in the file would notice, since not one of them would move — is a form read dot by
dot again, and it fails. Fewer rows for the same items is an improvement and passes, and
so is placing *more* items, which is what a reading that finds less does; a document with
nothing placed before is never a regression from nothing. The same rule answers for the
per-page drawing: more pictures for the same boxes is the leader pattern being answered
row by row again.

A rate is not a floor, though, and that is the other half of the rule. It keeps any
*proportional* fall — half the items answered in half the rows is the same ratio and half
the panel — and at the limit it reaches nothing at all: a document whose form is answered
no more is 0 rows for 0 items, which no ratio refuses, so the items can leave the panel
entirely with every number above unmoved. The **placed items themselves** are therefore
ratcheted as a count per document too: they may only fall on a document that placed
nothing to begin with, and a fall fails naming the document and the count
(`form item(s) placed: 327 → 160 item(s) in 12 row(s)`). That floor yields to nothing
else, because no other count in the file can tell a form answered as *text* instead from
a form lost; a reading change of that kind is argued for like every other deliberate
trade, by regenerating the baseline and reading its diff.

The **window**, the **corpus report** and the **command line** hold a reading to this
same ratchet: it lives in the library (`crates/ui/src/diff.rs` and `gate.rs` —
`Numbers`, `Memory`, `Report::hold_to_floor` and the one `Session` all three run their
documents through), this file is found by the Compare mode beside the references it is
about, and a finished document that falls below it is *refused* — the panel withholds the rows and names what
fell (`below the floor · form item(s) placed: 654 → 327 item(s) in 25 row(s)`), and the
CLI's `--compare test-data/golden/docling` exits non-zero naming the same document and
the same count, so a fallen panel fails a build and not only a window. The floor applies
whatever the run was measured with; the other rules — `differs`, the one-sided rows, the
character agreement, the rates — apply when the run's settings match this file's
`measured` block, which is what keeps the window's default `--ocr auto` from firing
against a baseline measured with OCR off. The panel says which of the two happened, per
document: a line reading `Held to the memory: …` names the rules that applied and the
two measurements that decided them, so a whole-ratchet pass and a floor-only one are
told apart on the panel itself. What is measured here, what the panel refuses
and what the gate fails on are therefore the same numbers from the same functions, and
this file is the memory of all three. The measurement is
deterministic (the corpus is converted with `--ocr never`, so no tessdata build is
involved), so a failure is a real change in a reading rather than noise. A plain image
is not in this ratchet: its text exists only through OCR, and converting one with
`--ocr never` would remember a page with no content. Its reference is held by the
golden suite's OCR comparison, which runs the image the way a reader would. When a
trade is deliberate, accept it on purpose:

```bash
CORPUS_BASELINE=update cargo test -p pdfextractor-ui --test corpus_report_test
```

which rewrites the file from that run — and the diff of `compare-baseline.json` is then
the argument for the trade, in front of whoever reads it beside the change. (`.gitignore`
carries an exception for this one file, since `*.json` is ignored repo-wide.)

## What the references are, per format

* **PDF, DOCX, RTF, XLSX, PPTX, images and Markdown** are read by Docling's own
  backends, so the reference is Docling's reading of the file. `inventory.xlsx` —
  the XLSX parser's fixture — `q3_review.pptx` — the PPTX parser's —
  `invoice_scan.png` — the image parser's — and `merged_table.rtf` — the RTF
  parser's merged-table fixture — are not in `test-data/real`: they sit beside the
  corpus, and the golden suite finds them there, so a format can be held to a real
  conversion before it joins the corpus and its ratchet. Docling reads an RTF
  through the same word-processor backend as a `.doc`, so the fixture's merged
  table and its headings have a reference of their own.
  `nested_table.docx` is written by `test-data/make_nested_table_docx.py`: an outer
  table whose second row's detail cell holds two of its own sentences around a table
  of its own (a step and who owns it), and nothing else in the package is a table.
  Docling reads it as **0 pages and four text items** — the heading, the framing
  sentence, and the cell's two sentences as items of their own — and **two tables**:
  the outer one, whose detail cell is a `RichTableCell` pointing at a group that holds
  those two sentences and the nested table, and the nested one under that group. Our
  reading is the same shape: the cell's `ref` names the group, the nested table is its
  child there, and the cell's text is its two sentences. The comparison reports **0/0
  pages and text agreement 1.000**, with two rows only the reference has — the cell's
  two sentences, which we hold inside the cell rather than as items beside it (Docling's
  rich cell is the subject of the text bullet below).
  `a_nested_table_docx_conforms_to_the_docling_schema` holds our output for it to the
  schema like every other fixture here.
  `invoice_scan.png` is written by `test-data/make_scan_images.py`: a clean printed
  invoice, 620 x 350 pixels at 150 dpi. Docling's reading of it is one page of the
  same size, with all four text lines; the comparison reports **1/1 page, text
  agreement 1.000**, and the heading it marks `section_header` is a title here — both
  are headings, which is what the label check asks. Its reference reports
  `origin.mimetype` as `application/pdf` (Docling's image pipeline leaves the PDF
  type in place); ours reports `image/png`, which is what the file is. The comparison
  does not look at the origin. The same scan in JPEG, TIFF, BMP and WebP lives in
  `test-data/images/` and is held by the parser and CLI tests to the page facts each
  encoding's own header declares.
  `q3_review.pptx` is written by `test-data/make_deck_pptx.py` and carries three
  slides of titles, master-bulleted and auto-numbered text, a multi-run paragraph, a
  merged-cell `graphicFrame` table, a picture, a chart (two series, one point left
  out as a gap), speaker notes on the first and last slide and three comments from
  two authors. Docling's reading of it is what the PPTX comparison is held to:
  **3/3 pages, text agreement 1.000**, every heading kept. The chart is part of that
  agreement: the reference holds the picture's classification (`bar_chart`), the
  reconstructed `tabular_chart` grid — series across the header row, categories down
  the first column, the missing point a blank cell rather than a zero — and the title
  as a `caption` item the picture points at, with no image on either side.
  The notes layer is part of that agreement: the reference holds the notes and the
  comments (Docling reads them too), and our output has to hold the same characters —
  the note on its slide's page with an empty box, and each comment in a
  `comment_section` group named `comment-slide<N>-<idx>`, its text the
  `[author: …, time: …]: …` string the two tools compose the same way. python-pptx
  cannot author a comment, so `make_deck_pptx.py` writes those parts into the saved
  package itself — the authors part, one comments part per slide, their relationships
  and their content-type overrides — which is what PowerPoint writes.
  Its reference reports `origin.mimetype` as the presentation **template** type (a
  constant in Docling's PPTX backend, whatever the file is); ours reports the
  presentation type, which is what the file actually is. The comparison does not look
  at the origin.
* **Legacy `.doc`** is not: Docling shells out to **LibreOffice** to turn a `.doc`
  into a `.docx` and reads that (`convert_to_modern_format` in
  `docling.backend.docx.drawingml.utils`). The four `.doc` references are therefore
  LibreOffice's reading of the file, and two consequences follow:
  * **fields are re-evaluated when the reference is made.** The footer of
    `FloatingPictures.doc` is stored as `Page 2` and `4/26/2006`; LibreOffice rendered
    it as `Page 7` and the day the reference was generated instead. Those characters
    cannot match a parser that reports what the file stores, so the four `.doc`
    comparisons sit at 0.94–1.00 rather than 1.00 by construction, and regenerating
    them changes the numbers a little. We report the stored results, which is what the
    document says. The day is the one character of this that a comparison cannot be
    asked about — the reference holds *its* conversion's day forever and ours holds
    today's — so the character share leaves a calendar value out of both sides (see
    the last of the limits below).
  * **LibreOffice's own style names can appear as text.** `testPictures.doc`'s
    reference contains a `Caption` item that is nowhere in the file — it is a paragraph
    style of the converted document. This is why the `.doc` references are a content
    cross-check rather than an exact expectation.

## Our own render goldens (markdown, html, text, yaml)

Beside Docling's *references* — one file per document holding the other tool's
reading, compared for content — four directories pin what **our own writers
produce**, byte for byte, for seventeen documents they all share: a one-line PDF
(`hello.pdf`), a one-paragraph PDF (`dummy.pdf`), a long form with tables and
furniture (`irs_f1040.pdf`), a DOCX with lists/tables/pictures
(`calibre_demo.docx`), a DOCX of Office Math (`math-accents.docx`), an HTML file
(`flow.html`), an HTML file whose table declares its header row below a caption
(`late_header.html`), the same late header with merged header cells
(`late_merged_header.html`), an HTML page whose picture's file name carries a space and
an ampersand (`picture_names.html`), a Markdown file read back (`fenced.md`), a
Markdown file whose picture is a real JPEG beside it (`pictures.md`), a purpose-built DOCX whose one
table merges cells (`merged_cells.docx`), the same merged table as a word
processor's own RTF export (`merged_table.rtf`), the link fixture
(`link_annotations.pdf`), a deck whose only picture is a drawing with no file
(`chart_deck.pptx`, below), and an RTF export whose content is a picture
(`rtf_bitmap.rtf`). The two merged-table fixtures are one reading in two
languages: HTML writes `rowspan="2"` and `colspan="2"` for each, Markdown and
text flatten the cells the spans cover to empty ones, and YAML states every
cell's spans. The RTF one is a brief authored with python-docx and exported by
LibreOffice, so it pins the flow reader beside the package reader — a wide cell
with no `\clmgf` at all read as a span, the vertical merge read from `\clvmgf`,
and headings recognised from stylesheet names because the export states no
`\outlinelevel` — and its header row is the first-row default, since that export
drops `w:tblHeader`: what its goldens pin is the fallback rather than a marker.
`late_header.html` pins the writers' hoist: the source writes a `colspan="2"`
caption row above `<th>Month</th><th>Total</th>`, while its Markdown puts the
names above the separator and its HTML puts them in `<thead>` with the caption
as the first body row. Its text and YAML goldens keep the same reading, and the
fixed-point gates read both renders back, so moving the header is pinned rather
than only asserted in a unit table. `late_merged_header.html` asks the second
question of the same hoist: its header row is also written after a `colspan="3"`
caption, but the row itself merges — `<th>Region</th><th colspan="2">Totals</th>`
— so the Markdown header has to keep the covered slot as an empty cell
(`| Region | Totals | |`) while the HTML keeps `colspan="2"` on the `<th>`. Both
renders put that row first and the caption beneath it, and the fixed-point gates
read each back into the same page.

`pictures.md` is pinned in all four: Markdown writes
`![Image](pictures_images/img1.jpg)` — the picture path a reader can follow —
HTML writes `<img src="pictures_images/img1.jpg">`, YAML lists the picture item
with its URI, size and type, and text pins that a reading with no pictures in it
leaves the picture out rather than leaving its markup behind. Every writer's
answer to the same fixture is therefore reviewed, not only the Markdown one.

For HTML the copy is checked as a copy and not only as a reference:
`the_html_golden_picture_is_copied_beside_the_page` converts `pictures.md` with
`--to html`, requires the page to name `pictures_images/img1.jpg`, and then reads
that file from beside the page and holds it to the JPEG the Markdown named, byte
for byte. A page that pointed at a picture no writer had put there would render
with a broken image, and the reference line alone cannot tell the difference; a
re-encoded copy would load, and the bytes can.

`picture_names.html` makes the same point for a name that HTML has to escape: the
picture is `images/Q3 chart & graph.gif`, the page writes
`<img src="images/Q3 chart &amp; graph.gif">`, and the pin is found by the name
the attribute stands for rather than the spelling it is written in — so the file
beside the golden is the one a browser would load, and the fixed-point gate reads
the escaped reference back into the same name. Markdown writes the same path in
`<…>` because it holds a space, and YAML states it unescaped; each golden carries
the spelling its own syntax asks for.

* `markdown/` — regenerated with
  `UPDATE_GOLDEN_MD=1 cargo test -p pdfextractor-cli --test md_golden_test`
* `html/`, `text/`, `yaml/` — regenerated with
  `UPDATE_GOLDEN_FORMATS=1 cargo test -p pdfextractor-cli --test formats_golden_test`

A golden pins **the files it names**, not only its own bytes. Each rendering is
converted into a directory of its own, the references in its text are read back —
Markdown's `![Image](…)` and `[…](…)`, HTML's `<img src="…">` (the attribute's
value decoded first, so an escaped `&amp;` names the file `&` stands for), and the
document model's YAML `uri:` — and every one of them is held to a copy committed beside the
golden under the same relative path (`markdown/pictures_images/img1.jpg`, say). A
copy that was re-encoded, truncated or emptied still satisfies the reference, so
the bytes themselves are the pin; a reference to something the run did not write
is a failure, and so is a pinned file no golden names any more. The discovery is by
reference rather than by case in `crates/cli/tests/common/mod.rs`: a document that
starts naming a new picture is pinned by the same test, and the asset directories
of the whole set are swept once per format so one document's pictures are not
mistaken for another's leftovers. Regenerating writes the pins from the same run,
so the diff of the images is the review just as the diff of the documents is.

Both harnesses run the real binary with `--ocr never`: recognised text depends on
the installed Tesseract's language data, which would make a byte-exact golden flaky
on machines that are otherwise correct. `--to text` runs with its documented
default, hyphenation joining on. The Markdown goldens are also generated with
`--include-notes`: `q3_review.pptx`'s golden carries its speaker notes and comment
sections, so the notes layer is part of the pinned bytes instead of being exercised
only by hand-written cases. These goldens are our own render decisions recorded as
bytes — a render change moves one, and the diff of the moved goldens is the review.

`inventory.xlsx` joins the Markdown set on the other side of the model: a workbook
is read as one `sheet` group per worksheet, holding the worksheet's tables, and
groups are marked in Markdown with the same invisible comments a deck's slides use.
The workbook's golden is therefore where that grouping is pinned — `Inventory` and
`Notes` each open a `sheet` group named as the workbook names them, and each group
holds the tables that sat under it, while the hidden worksheet stays on the
`invisible` layer and so appears nowhere in a body-only rendering.
`a_workbook_pins_a_sheet_group_per_worksheet` states what those bytes are for rather
than leaving it to the diff: it reads the golden and requires the two groups, their
order, their names, and their tables inside them — then reads the golden back and
requires the JSON to hold the same two `sheet` groups with the same children, which
is how a grouped workbook has to survive being saved as Markdown. No committed
HTML, text or YAML golden was added: the workbook's sheet markers are the same
`<!-- pdfextractor:group … -->` comments those writers emit, so what needed pinning
is the group structure, and the two gates that consume the Markdown set — the
fixed point and `every_golden_round_trips_through_html_with_notes` — already walk
every case in it, inventory included.

`rtf_bitmap.rtf` is the other kind of case: a **word processor's own file**, not one
written to show a feature. It is LibreOffice's export of a DOCX holding a small bitmap
(the script that makes it is `test-data/make_rtf_fixtures.py`), so what the reader has
to survive is what an exporter actually writes — a font table full of fallback faces, a
stylesheet, `\pard` and `\plain` soup around every paragraph, and a picture carried as
a `\pngblip`. All four writers pin their answer to it: the heading at its depth
(`## A word processor's bitmap` — a `section_header` at level 1, which Markdown, HTML,
text and YAML each write their own way), the paragraph before the picture and the one
after it, and the picture itself under `rtf_bitmap_images/img1.png`, whose PNG is
pinned byte for byte beside each golden that names it. The text golden is the one that
shows the mode's honesty: a rendering with no picture syntax says neither `![Image]`
nor anything else about the image, only the words around it. Its HTML is its own bytes
too — an empty `<title>`, because an RTF export from a DOCX with no title has none,
which several goldens already say. `merged_table.rtf` is the same kind of case for
tables (see the merged-cell section below): an exporter's own spelling of a table
that merges both ways, with the headings it recognises from style names.

The Markdown goldens are also the round-trip gate: `every_markdown_golden_is_a_fixed_point`
(no environment variable, it runs with the rest) reads **every** committed `.md` in
`markdown/` with the real binary and renders the read document back to Markdown; the
re-rendering must equal the golden **byte for byte**. Both passes are given
`--include-notes`, so a remark has to come back on the notes layer rather than as a
paragraph of the page. It then reads that rendering
again and requires the item list (labels, text, depths, markers, links, content
layers, table cells, picture media types and sizes) and both renderings to agree —
so the reader is the writer's inverse for every construct the goldens carry, and
that inverse is stable. A speaker note is headed `**Notes:**` and a comment
`**Comment:**`, and the reader keeps the kind, so a reviewer's remark stays a
comment rather than becoming one more presenter's note.
An image a golden names is not beside the golden `.md` in `markdown/` — the copy
lives under the asset directory beside it — so a reader handed that one file alone
finds the literal text the reference becomes, which is exactly the stable thing to
be; the pinned copy is what proves the bytes. A `$$` block is read back as a
`formula` item, so the math golden reproduces itself instead of being flattened
into three paragraphs. The gate is
what makes the reader the writer's inverse: headings are read at Docling's depths
(`#` is the title, `##` a level-1 section header), so a rendering neither gains nor
loses a level when it is saved again. `fenced.md`'s golden moved with that reading —
its `#` heading now writes as `#`, not `##` — in Markdown, HTML, text and YAML, and
the move is the review.

The HTML renderings have the same gate: `every_html_golden_is_a_fixed_point` (in
`formats_golden_test.rs`) reads **every** committed `.html` in `html/` with the real
binary and requires the page it re-renders to equal the golden **byte for byte**. A
page's pictures are copied to where its own `src` resolves before it is read — a
golden that names a file is only the same page if the file is there — which is also
why the gate is a statement about *names*: a flow page's own picture keeps the path
the page gave it (`images/scan.jpg` stays `images/scan.jpg`), and a table cell is
written with every run of whitespace made one space, the only spacing a page can
hold and a reading give back. Without those two the page could not be its own bytes,
and the gate would have to except exactly what a page cannot say.

The pictures have a gate of their own:
`every_golden_renders_embedded_to_its_referenced_pictures` (its own test file,
`crates/cli/tests/picture_fixed_point_test.rs`) walks **every** committed golden in
both `markdown/` and `html/`, converts it with the default `referenced` image mode
and again with `--image-export-mode embedded`, and then reads the embedded page
back. The embedded page has to carry the referenced render's picture bytes — the
same count, types and sizes, and the bytes themselves, not a re-encode — and the
re-read document has to write those same bytes again and re-render the embedded
page unchanged — the whole page, `<title>` included, since the title is the
document's own rather than the name of the file that was read. A picture's bytes
are held just as strictly. Each golden is rendered `placeholder` as well, and
that page must mark every picture once and name none: no `_images/` file, no
`data:` URI, no `![…](…)` or `<img>`, and — where every picture has a file — the
referenced page with each picture block replaced by `<!-- image -->`, byte for
byte. Reading a golden where it
sits matters here: the referenced files are the ones the gate compares, so moving
the golden to a scratch directory first, as the Markdown fixed point does, would
turn every picture into its literal text instead.

A picture with no bytes is the case the gate could not reach by reading a golden,
because a referenced page has already forgotten one: it wrote no block to point
at. `chart_deck.pptx` (written by `test-data/make_chart_deck_pptx.py`) is that
document — one slide, a title and a sentence, and a chart, which the model holds
as a `PictureItem` with a `tabular_chart` and no `image` at all. The placeholder
pass therefore reads the document a golden was rendered *from*, found by the same
file stem the Docling comparison looks documents up by, and falls back to the
golden itself for a document that is not in the repository. Its mark has no
referenced block to stand in for, so the correspondence is drawn block by block
instead of byte by byte: the pages are walked together, a mark may stand where a
picture block was and may be inserted where a drawing stood, and every other block
has to be the same block in the same place — so a mark at the top of a page for a
picture at the bottom fails, and so does a paragraph hidden under one. The gate
names `markdown/chart_deck` and `html/chart_deck` at the end, so the branch cannot
stop being covered without failing.

The other reader has its own gate: `every_golden_round_trips_through_html_with_notes`
writes each document as HTML with its notes, reads that HTML back with the real
binary, and requires the Markdown it renders to be the Markdown written directly
from the document. Only two things are excused, because HTML cannot keep them: the
file names this run gave its pictures, and the runs of spaces an HTML cell collapses
(table rows are compared by their cells' words, not their padding). Everything else
is byte for byte — headings, groups, notes and comments with their `Notes:` and
`Comment:` labels, code, formulas, and tables (flattened in the Markdown both sides
write, whatever the model held). A second pass reads the HTML-derived Markdown and renders it again, so the
HTML reader and the Markdown reader have to agree with each other and with the
writers, not only pass their own inverses. Making that pass possible closed four
reader gaps: `h1` is a `title` and `h2` a level-1 header, `<pre><code>` is a `code`
item with its lines, and `<div class="formula">` is a `formula`. A cell's
`rowspan`/`colspan` is the span the cell covers — one cell placed over its slots,
the slots it merges holding none, rather than an empty slot beside a cell that only
looks wider — so the grid the HTML reader puts in the model is the merged table the
page declared, and the outer HTML writer writes those spans back unchanged. The writers also carry group markers
in HTML as the same invisible comments Markdown uses, and a printed marker `<ol>`
cannot spell (`1.1.`) in `data-marker`, with `<li value>` keeping a list's resumed
number.

Text and YAML each have the same gate, in the same file as the format goldens
(`crates/cli/tests/formats_golden_test.rs`). `every_text_golden_is_a_fixed_point`
reads **every** committed `.txt` in `text/` with the real binary and renders it
back as text, which must be the golden byte for byte; a second pass reads what the
first wrote and renders it again, so the re-rendering is stable rather than right
by accident. That gate is what the plain-text reader is shaped by: text states one
boundary, the blank line, so a run of non-empty lines is one block — a single line
is a paragraph, and a longer run is written back verbatim as a `code` item, since
the writer folds a paragraph's own lines onto one, and a run opening with the
writer's grid (`| a | b |` over `|---|---|`) is the table it is. Read one line at a
time instead, a code block would lose its indentation and a table would gain a
blank line between every row on each save.

`every_yaml_golden_is_a_fixed_point` is the model's rather than a reading's: it
parses each committed `.yaml` in `yaml/` back into a `DoclingDocument`, renders it
again, and requires the golden's bytes — then renders the result once more to prove
it settles. Nothing is converted from a source document, so what it pins is the
notation and the ordering: a key that moved, a `self_ref` rewritten a second time,
or a `pages` map that came out in another order (it is a hash map; the writer sorts
it) shows up here and nowhere else.

Merged cells used to be the one gap in that set — no document in the corpus had a
table with merged cells, so the HTML writer's `rowspan`/`colspan` fidelity rested on
hand-written unit tables. `merged_cells.docx` opened it with a fixture (written by
`test-data/make_merged_cells_docx.py`) whose table declares every merge
WordprocessingML has — `w:gridSpan` on the header cell, `w:vMerge` down the class
column, `w:tblHeader` on the first row — and `merged_table.rtf` reads the same
table through the flow path: `test-data/make_merged_table_rtf.py` has python-docx
author that brief and LibreOffice export it, so the RTF reader's own merge
spellings (a wide cell with no `\clmgf` at all, the vertical merge stated with
`\clvmgf`) and its `Heading N` recognition are held to the same four renderings.
The two pairs of goldens hold the readings apart side by side: HTML writes the
merges as native `rowspan="2"`/`colspan="2"` with the covered slots not written at
all, Markdown and text flatten the same table (the merged cell's words once, its
covered slots empty), and YAML lists the spans in the document model. The corpus
carries merged tables too — `calibre_demo.docx`'s December calendar spans thirteen
columns and its nested table merges two rows — so the same fidelity is pinned on a
real document's goldens as well. Its nested table is a table inside a cell, so the
goldens pin that reading too: the outer table's cell holds the nested cells' words
(`One Three Two Four`) in all four renderings, rather than the nested table standing
beside the outer one as a table of its own.

The goldens also pin the hyperlink split. `calibre_demo.docx` and `flow.html` each
carry a linked sentence, and once `TextItem.hyperlink` was filled from a DOCX
`w:hyperlink` and an HTML `a[href]`, both documents render as three items where they
rendered as one: the words before the link, the link's words (the only item holding
the URL), the words after. Their Markdown, HTML, text and YAML goldens moved together
— YAML, which lists the model, now shows the URL — and the diff of those files is the
review that the split lands where Docling's own references split it.

Where a link reaches a writer, the writer says so: Markdown writes
`[text](url)` and HTML `<a href="url">text</a>` around the item's whole text,
because the model holds one URL per item and no span offsets. `calibre_demo.docx`
and `flow.html` gained their `[calibre download page](…)` and `[link](…)` when
the writers learned the field, and `link_annotations.pdf` was added to the set so
a PDF `/Link` annotation is pinned too — with its YAML showing the URL on the
item, and its text golden unchanged (a reading has no markup). The `text` writer
keeps leaving links off: a URL around words is a rendering, not a reading.

## Regenerating the conversions

`regenerate.py` needs the full `docling` package (2.138.0 with docling-core 2.101.1 for
the committed copies), which pins its own model and layout versions, so the output
depends on the Docling version. LibreOffice is needed for the `.doc` files.

```bash
cd test-data/golden
~/.venvs/pdfextractor-docling/bin/python regenerate.py $(ls ../real)
```

The PDF pipeline runs layout and table models on CPU, at roughly a minute per page for
the papers here: the whole corpus is about an hour of wall clock, and the seven PDFs are
most of it. Generating a new document is seconds to a minute; committing its reference is
what makes the comparison permanent. A fixture beside the corpus is named the same way,
by file name (`python regenerate.py inventory.xlsx`, `python regenerate.py
invoice_scan.png`), and its reference lands in `docling/` like any other.

Regenerate when the schema is updated: a reference from an older docling-core
carries the older `version` and will make the comparison noisy for reasons that
have nothing to do with extraction.

## What the comparison does and does not compare

`compare()` in the test file compares **content**, because the two tools
disagree about layout *by design*: blocks are segmented, labelled and ordered
differently, and Docling splits a paragraph at every formatting run where we keep
one paragraph. A reference can also contain *more* text than its source file:
Docling repeats some of it (six copies of a table cell the file holds four times,
73 occurrences of a name a `.docx` holds 68 times). That shows up as agreement
below 1.00 and is not a loss on our side — where it mattered, the source file was
counted instead (`pdftotext`, the `.docx` part, the Markdown itself).

Compared:

* **Pages** — same count, and every page size within a point.
* **Text** — the reference's alphanumeric characters, as a multiset (a character
  the reference repeats twice must appear twice here), over both text items and
  table cells. Agreement must be ≥ 0.85; the corpus documents are at 0.991–1.000.
  A cell that holds more than one block — a *rich* cell, its `ref` naming a group of
  its own content — is counted **once, not twice**: Docling writes such a cell both as
  the cell's text (its paragraphs joined) and as those paragraphs standing inside the
  cell's group, so what the cell's text contributes is only what its group's paragraphs
  do not already hold. Nothing is taken out for a table nested in the cell: a cell's
  text is its own paragraphs, never the nested table's, and those cells are counted
  where the table stands. Without that rule a table in a cell made the reference look
  as if it held the cell's sentences twice — `nested_table.docx` read 0.815 — and a
  reading holding every character looked like a loss. The panel's comparison applies
  the same rule (`characters` in `crates/ui/src/diff.rs`), so the two figures stay one
  metric.
* **Equations** — a document that contains *n* equations must report *n* of them.
  Every reference with formulas matches exactly today. Only the reference's formula
  items **that carry text** are counted, because a PDF reference can hold empty formula
  boxes: its layout model's idea of where an equation sits, with no characters recovered
  for it. There is no equation in one to be found, so a document with six empty boxes
  is not a demand for six items from us. The full count is printed either way.
* **Duplication** — no block may appear twice in a row. This is a defect
  whatever the reference says about segmentation, and it is what found Word's
  `mc:Fallback` copy of every shape (bug 46). Text drawn inside a figure is the
  one exemption: a chart repeats a legend under each subplot and the attention
  visualisation in `arxiv_attention.pdf` prints every word twice by design, so a
  repeat whose box lies inside a picture is the drawing and not our extraction.
* **Labels and boundaries** — a heading read as body text, a block that merged
  across a boundary, a table's cells read as prose. See the section below: this
  is the part of the comparison that asks whether what was found is the *right
  thing*, not merely whether the characters are there.

Not compared, deliberately:

* **Formula command characters in the text agreement.** Docling writes LaTeX
  (`\iiint_{V}^{}divFdV`), and so do we. Each reference formula carrying text must
  appear among ours as the same LaTeX with whitespace ignored — spacing is layout,
  a different command is a different notation — so all 38 equations across the 14
  formula-bearing references are compared. Their command letters are kept out of the
  character multiset, where `\frac` would count as text, and the equation counts still
  catch a document that reports fewer equations than the reference.
* **How finely text is split.** Docling reports a paragraph of prose split at every
  formatting run, and emits empty items for the runs it has nothing for; we keep the
  paragraph whole. Item *counts*, and therefore where one boundary of ours sits
  relative to the other tool's, are not compared for that reason. Some of the residual
  agreement on `calibre_demo.docx`, `README.md`, `drawing.docx` and the `math-*.docx`
  files is exactly this. The label comparison below is anchored by characters instead,
  so segmentation cannot hide a mislabelled heading.
* **Bounding boxes.** Flow formats (DOCX, `.doc`, RTF, HTML, Markdown, text)
  have no page geometry on either side, so there is nothing to compare; PDF
  boxes are covered by the layout suite's own invariants.
* **Docling's `$...$` convention outside a matched pair.** Docling writes inline math
  between dollar signs, so `$x^2$` is not counted — but a form that prints a price
  (`$15,750`) or a fund election (`...want $3 to go to this fund`) has a single `$` in
  an item, and the text after it is text. Only paired dollars are treated as notation
  (bug 48). Treating each `$` as a delimiter made the IRS form look like a 29% loss
  when our output held every character of it.

## Labels and boundaries

Content agreement asks whether the characters are there. This asks whether they
are there **as the right thing**, which is a separate way for a document to be
wrong: a heading read as body text has lost a boundary, a table read as prose has
lost a table, and every character can still be present.

The two tools segment differently, so nothing here compares item counts or
boundaries by index. A reference item is anchored in ours by its **characters
alone** (alphanumerics, after Docling's paired `$...$` inline math is removed),
which makes whitespace, punctuation, line breaks and hyphenation irrelevant.
Three things are then checked:

* **Headings.** Every reference `section_header` or `title` must be under a
  heading or title label of ours. One we hold only as body text is a mislabelled
  heading *and* a boundary we did not draw. Reference headings whose text is
  absent altogether are left to the text agreement, which already measures them.
* **Boundaries.** A structural block of ours — a heading, title or caption — must
  not hold a reference body block of comparable size (≥ 40 characters, and at
  least 40% of our block). A paragraph that swallowed its heading is the case
  this catches, from the other side. Docling's fragments of a line inside one of
  the same blocks are too short to count, which is what keeps it from firing on
  every paragraph.
* **Tables.** A reference table cell must be inside one of our tables. A cell we
  hold as prose **under a table of ours** is reported as a failure — the text was
  found, but on the wrong side of a table boundary. A cell we hold as prose with
  no table of ours covering it is *counted and printed* instead: our table
  detection is deliberately conservative (see `progress.md`), and pretending it
  is not would mean asserting a fix nobody has made. The counts are printed for
  every document on every run, so the size of that gap is visible rather than
  remembered.
* **Footnotes.** Every reference `footnote` must be one here. A note we hold as
  body text is the interesting failure — the page drew its rule and its marker and
  we read past both — and a note whose opening is absent altogether is a loss the
  character agreement has already measured, *or* its text was read as a **table**: a
  table's cells are not text items, so a note block taken for a grid shows up as an
  opening that is nowhere rather than as a mislabelled line. A note is matched by its
  **opening** (24 characters), not in full, because the two tools cut a note
  differently: Docling keeps the whole note and we may keep a fragment of it, or the
  other way round. Both counts are printed for every document on every run: today **two**
  notes are read as body text (`tracemonkey.pdf`'s, whose pages draw no rule) and **none**
  is missing.

### The footnotes

`FOOTNOTE_BUDGETS` in `crates/cli/tests/docling_golden_test.rs` allows what the
comparison measured, and it has **two floors** per document: the notes we **hold** —
labelled `footnote` or, failing that, still in the body — and the notes we **label**,
because the two failures are different and only one of them is the pass's doing. Every row
below is at both of its floors, and every floor is the whole of Docling's count: not one
reference note is missing from the output.

| Document | Reference notes | Labelled `footnote` | Held (kept + read as text) | Why the rest are held as body text |
|---|---|---|---|---|
| `arxiv_attention.pdf` | 5 | 5 | 5 | All of them. |
| `math_layernorm.pdf` | 5 | 5 | 5 | All of them: notes `2`–`5` used to come out as a **table** — two notes on a page are two rows of marker-and-text — and the page's rule above them hands the block to the note pass instead (below). |
| `math_seq2seq.pdf` | 9 | 9 | 9 | All of them, now: `∗CIFAR Senior Fellow` opens with a `∗` the page sets in a TeX symbol font, and the font program's own encoding is read (below). The four that used to be read as a **table** (`3`, `4`, `6`, `7`) are labelled too. |
| `math_gan.pdf` | 4 | 4 | 4 | All of them: the three author lines of the arXiv note were paragraphs because their `∗`/`†`/`‡` markers are drawn in the same symbol font and came out as nothing, `y` and `z` (below). The fourth is the `1` note. |

The four PDF documents of the comparison with no reference footnotes (`basicapi.pdf`, `dummy.pdf`,
`irs_f1040.pdf`, `math_batchnorm.pdf`) get none, which is the false-positive side of
the measurement: two lines that used to be read as notes — `arxiv_attention.pdf`'s
`31st Conference on Neural Information Processing Systems (NIPS 2017)` line and a
reference-list item opening `1:` — open with a number, but not one the body of their
page uses, and the pass no longer takes them (Docling reads the first as
`page_footer`, the second as a list item).

All **27** reference notes are held — **25** under a `footnote` label and **2** as the
paragraph they were read as — and **not one is missing** from the output, which is also
the statement that no note is inside a table any more.

Two marks only the page had moved the rows above, and each is now read:

* **The rule the page draws above its notes.** A note block is two rows of
  `marker | text`, indistinguishable from a small table by geometry alone, and layout used
to be given only the text — so it built the grid, and the note pass, which reads *text*,
could not see the notes inside it. `analyze_page` now takes the page's rules, and a note
candidate standing in the foot *under a rule* is handed on as rows rather than as a table
(`groupings_in`): the mark that says "these are notes" is the same one the pass reads, and
a page does not draw a rule over a table.
* **The encoding the font program carries.** The `∗`/`†`/`‡` of a TeX note are set in
`CMSY`, and a symbol font declares no `/Encoding` in the PDF: its codes are the font
program's, which puts `asteriskmath` (\u{2217}) at code 3 and `dagger`/`daggerdbl`
(\u{2020}/\u{2021}) at 121/122. Read as Latin-1 those are a *control character* — dropped
by `sanitize` — and the letters `y`/`z`, so the marker the pass follows was simply not in
the text. `parse_type1_encoding` now recovers the `dup <code> /<glyph> put` array from the
embedded program and `glyph_text` names it, and `math_gan.pdf`'s three author lines come
out as `∗`/`†`/`‡` notes where they were `y…`/`z…` paragraphs.

`progress.md` records both. What is left is the **2** notes held as body text:
`tracemonkey.pdf`'s, whose pages draw no rule above them at all. That is a limit of the
page, not of the pass.

## Where we are more complete than the reference

The comparison is about what the reference saw, so it does not force us to
*reproduce* an omission:

* **Chart titles in the `cx:` namespace.** Word's modern chart types write the
  title under the `cx:` namespace; Docling reads `c:title` only. We read both,
  so `chartex.docx` reports its box-and-whisker and sunburst titles as captions
  and Docling does not. Removing them to match the reference would lose content.
* **Equations at the edge of a DOCX paragraph.** Docling splits them out and leaves an
  empty text item behind; we split them out and leave nothing (bug 47).
* **A TeX font's glyph names.** The names a Computer Modern font uses (`nabla`,
  `summationdisplay`, `bracketleftBig`, `epsilon1`, …) are named from its own encoding, so
  we hold `∇`, `∑`, `[` where the reference's PDF backend falls back to the Latin-1 byte:
  `math_gan.pdf`'s reference has 17 more `r` than we do and no `∇` at all, which is the
  same 17 glyphs. An extensible delimiter is reported as its character, once per piece the
  page draws it with, so `math_gan.pdf` holds 13 `}` to the reference's 4.

## Known limits this comparison measures

* **A `.doc`'s field results are the conversion's, not the file's.** A `.doc`
  read through the bridge is a `.docx` LibreOffice wrote, and LibreOffice
  evaluates the `PAGE`, `DATE` and `FILENAME` fields while it writes it, exactly
  as Docling's own `.doc` conversion does. So the two readings agree about the
  footer's page number and the document's name where the built-in reader (a
  machine without LibreOffice) reports what the file stores instead — `Page 2`,
  `4/26/2006`, the name the document was authored under. The `DATE` field is the
  one with no answer to hold: the reference holds the day *its* conversion ran and
  our reading holds the day it ran, so the character share counts neither — a
  calendar value written with numeric separators (`10/12/2026`, `4-26-2006`,
  `2026.10.12`) is dropped from both sides, and `FloatingPictures.doc` reads the
  same **99.3%** (0.99275) on any day. The value is what is left out, not the item: without
  those words the footer is still a row that differs or a row only the reference
  has, and both of those are ratcheted. Before the rule the same reading scored
  99.162% to 99.133% depending on the day, which is enough for the ratchet to
  refuse a reading that lost nothing the next morning. See `progress.md` for the
  whole accounting.

* **TeX math glyphs in PDFs, and what the *reference* does with them.** The glyph codes
  are the font program's, and we read them (above) — which is also why agreement now
  *falls* on three documents, by 0.02-0.15pp, where a Latin-1 substitute had been propping
  it up: a wrong character is still an alphanumeric, and it can be matching one the
  reference holds elsewhere. The corpus sits at 0.997-0.999 today except
  `arxiv_attention.pdf` at 0.994, and `math_layernorm.pdf` *rose* from 0.996 when its
  `∑`/`√`/`×` stopped being letters and digits. What is left of `arxiv_attention.pdf`'s
  residual is spread over both sides — characters the reference holds and we do not, and
  pieces we hold and it does not, such as the `⌈` it leaves out of `∈ Rdmodel× ⌈k` — and no
  single cause explains it, which is why it is measured and printed rather than asserted.
* **Text inside figures.** A figure included from another file is usually a form
  XObject, and its labels, legends and axis numbers are text drawn inside it. We read
  those now (see `progress.md`); that is what lifted `math_layernorm.pdf` from 0.976 to
  0.996 and `math_seq2seq.pdf` from 0.989 to 1.000. Docling's layout model keeps most
  of them too, so the comparison sees them on both sides — but where it drops one, we
  are the more complete document, and the agreement cannot rise above 1.000 to say so.
* **PDF equations are not labelled as formulas.** Docling's layout model marks 6
  equation regions in `arxiv_attention.pdf` and 19 in `math_batchnorm.pdf` (with no text
  recovered); we report their text as prose, which is where those characters live.

## Not here: Microsoft Works

The Works family's real documents are not committed, and not referenced. They come
from [libwps' OSS-Fuzz seed corpus](https://sourceforge.net/projects/libwps/files/corpus/),
which states no licence for its files — a fixture this repository cannot license is
one it cannot hold. They are read through LibreOffice, so a reference would have to be
LibreOffice's reading anyway (as it is for legacy `.doc`), and the test that holds the
bridge to a real file is opt-in:

```bash
PDFE_WORKS_SAMPLES=/path/to/works-wps cargo test -p pdfextractor-cli
```

The three `curl` lines that fetch the corpus are in the main
[README](../../README.md); the test skips itself when the variable is unset or no
`soffice` is on `PATH`.

**`test-data/real/README.md` is itself a compared document.** It has a Docling
reference of its own, so editing its prose moves the ratchet; notes about the corpus
belong here, or in the main README, rather than in the file the corpus describes.
